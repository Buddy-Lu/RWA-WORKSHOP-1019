### 03｜1-1 什麼是區塊鏈？（Canva 4；3:00–6:00）

先想像班級有一份點數帳本。傳統做法是由一個管理者保管資料庫，決定哪些更新能寫進去。區塊鏈把驗證與保存資料交給網路中的節點，節點依共同規則檢查交易，再對接受的狀態達成共識。

左邊是集中管理的概念，右邊是多個參與者共同驗證。右邊的人多，不代表任何資料都是真的；如果一開始輸入的股價是錯的，區塊鏈仍可能非常一致地記錄那個錯誤。它能幫我們檢查規則與紀錄，不能替我們看見銀行裡到底有沒有資產。

**提問：** 學校資料庫裡的點數和鏈上的代幣，都能顯示餘額，真正不同的是什麼？

**引導答案：** 寫入權、驗證方式與信任對象不同，不是有沒有一個漂亮的餘額畫面。

### 04｜1-2 什麼是挖礦？（Canva 5；6:00–8:00）

挖礦通常是在講工作量證明，也就是 PoW。參與者投入算力競爭產出區塊的機會，其他節點仍會驗證區塊是否符合規則。另一種方式是 PoS，透過質押與驗證者規則參與共識。

這張圖是比較兩種機制。Bitcoin 使用 PoW；我們今天操作的 Ethereum 已使用 PoS，所以不要把所有區塊鏈運作都稱作挖礦。今天你不用挖礦，也不用成為驗證者；錢包會把交易送進網路，由網路處理確認。

**銜接：** 共識決定網路接受哪些狀態，接下來看狀態更新的規則寫在哪裡。

### 05｜1-3 智能合約與代幣標準（Canva 6；8:00–11:00）

智能合約可以先理解成放在鏈上、按照規則執行的程式。例如轉帳要檢查餘額，買入要檢查付款，贖回要檢查儲備。程式把條件寫清楚，交易觸發後，節點執行相同邏輯。

ERC-20 是代幣常用的介面標準，讓不同錢包知道如何查餘額、轉帳與授權。符合這個介面，可以讓應用更容易整合；但名字叫台股，並不代表它自動擁有真實股票。介面規格與資產權利，是我們等等要分開看的兩件事。

**提問：** 把合約名字改成台積電，會自動讓券商帳戶多一股嗎？等同學回答後再進下一頁。

### 06｜1-4 燃料費 Gas Fee（Canva 8；11:00–13:00）

Gas 是衡量鏈上運算資源的方式。你要付的交易費，和你轉出去多少課程幣，不是同一個數字。今天即使用測試 TWD 付款，仍需要 Sepolia ETH 支付交易費。

這裡的截圖是介面示意，不是當下費率。一般從網頁查詢餘額不送出改變狀態的交易；部署、轉帳和授權則需要送交易。若交易已上鏈執行但失敗，狀態通常會回復，但已消耗的 gas 仍可能付掉。

**操作：** 指出「付款 token」與「網路費」在錢包裡的位置。提醒等一下 constructor 的 Value 保持 0，並不代表部署不花 gas。

### 07｜1-5 Layer 1 與 Layer 2（Canva 9；13:00–15:00）

用 Ethereum 和 rollup 作例子：Layer 2 承擔更多交易執行，整理資料與結果，再依其設計使用 Layer 1 提供的資料與結算基礎。不同 L2 的安全假設與運作細節還是需要分別了解。

對今天操作最直接的影響是：地址看起來一樣，網路不同，狀態可能完全不同。你在 Sepolia 部署出的合約，不會因為切到另一條鏈就自動出現。接下來所有操作都先確認鏈別，再確認地址。

## 15–25 分鐘｜第二單元：RWA 現實世界資產代幣化

### 08｜2-1 RWA 核心概念（Canva 10；15:00–17:00）

RWA 討論的是如何把現實資產相關的權利、紀錄或經濟安排，用鏈上的代幣呈現。看圖從左往右：先有資產，再有權利約定，最後才是代幣。程式可以發幣，但不能憑空補出中間那份約定。

所以做 RWA 的第一個問題不是選哪條鏈，而是持有人拿到什麼。它代表所有權、收益請求權、贖回權，還是只是追蹤某個價格？不同答案會影響保管、兌付與產品設計。

### 09｜2-2 資產與持有人權利（Canva 11；17:00–19:00）

同樣是顯示一個代幣餘額，背後可能是不同權利。假設我說這個代幣跟黃金或股票有關，你應該追問：資產由誰保管？我可以向誰請求兌付？有沒有條款或證據說明這件事？

今天我們不對特定商品作法律判定，而是建立閱讀系統的習慣。不要看到名稱、logo 或價格曲線，就跳到自己已持有那份現實資產的結論。先找權利安排，再看程式如何執行。

### 10｜2-3 鏈上與鏈下分工（Canva 12；19:00–21:00）

上半部是鏈下：保管、查核、契約與資料提供。下半部是鏈上：餘額、轉帳與合約規則。兩邊需要有可說明的連結，才能讓鏈上的紀錄對應到現實安排。

Oracle 可以把外部資料寫進合約，但它不是萬能證明。讀到一個股票價格，不代表合約已經替你買好股票。等一下我們會看到本專案有餵價程式，卻沒有券商下單與實股託管串接。

### 11｜2-4 台股代幣化案例（Canva 13；21:00–23:00）

這個教學原型用測試 TWD 支付，StockToken 讀 Oracle 價格，算出要發多少台股代幣。它能讓我們完整練習付款、鑄造、贖回與前端整合。

### 12｜2-5 儲備與兌付（Canva 14；23:00–25:00）

如果代幣可以賣回，合約就需要有資金支付。你可以把儲備想成可用來付款的池子；報價則告訴你這次應該付多少。報價正確與池子有錢，是不同檢查。

## 45–70 分鐘｜第四單元：ERC-20 與 Remix 發幣

### 19｜4-1 ERC-20 代幣標準（Canva 28；45:00–49:00）

ERC-20 提供共同介面。`balanceOf` 問某個地址有多少，`totalSupply` 問總供給，`transfer` 由自己轉出，`approve` 和 `transferFrom` 處理授權代扣。名稱與代號是顯示資訊；真正辨識這份 token，要看鏈別和合約地址。

今天每個人都可以叫自己的幣 NTHU，但它們仍是不同合約。你查同學的合約，不能期待看到自己那一份供給。共同介面讓錢包知道怎麼問問題，不會把所有同名代幣混成一份帳本。

**提問：** 兩個代幣都叫 NTHU，要怎麼分辨？請同學回答「網路與合約地址」。

這個例子用 18 位精度，所以輸入整枚數量後，程式乘上 `10 ** decimals()`。我們填 1000，就得到 1000 枚，不要把那一長串最小單位直接填進 wholeSupply。這份課程幣也沒有額外公開的 mint 入口。

### 22｜4-4 轉帳與餘額驗證（Canva 31；62:00–70:00）

現在請 A 轉 10 枚給 B。Remix 的原始 amount 要填 `10000000000000000000`，也就是 10 乘上 10 的 18 次方。若只有這一次轉帳，A 應該從 1000 變 990，B 從 0 變 10，總供給保持 1000。

## 75–105 分鐘｜第五單元：台股代幣化平台實作

### 23｜5-1 平台架構（Canva 32；75:00–79:00）

剛剛我們完成了獨立的 token，現在把鏡頭拉到完整應用。圖上有兩條資料路徑：網站 API 可以把行情送到畫面；另一條是 feeder 取得價格後送交易，把資料寫入鏈上的 Oracle。畫面更新和鏈上價格更新不是同一件事。

使用者透過瀏覽器與錢包呼叫合約。keeper 則是另一個程式，觀察可清算的部位再送交易。前端、feeder 和 keeper 各有不同責任；把網站打開，不代表另外兩個程式就會自動運行。

**操作：** 在 GitHub 指出 `frontend/src`、`frontend/api`、`onchain/contracts`、`onchain/scripts`。讓同學先建立目錄地圖，不逐檔展開。

### 24｜5-2 鑄造與贖回（Canva 33；79:00–84:00）

StockToken 仍然是 ERC-20，但多了業務規則。買入時，使用者先授權 TWD，再呼叫 mint；合約轉入 TWD、讀價格、換算股數、更新儲備並鑄幣。贖回時，合約先算應付金額，確認儲備足夠，再燒掉使用者的股票代幣並轉出 TWD。

請注意精度：TWD 是 6 位，股票代幣是 18 位，不能直接拿兩個原始整數相比。還有一個差別：這個 StockToken 的 redeem 是燒呼叫者自己的餘額，因此這條路徑不用先 approve 股票；如果是借貸池來代扣，規則就不同。

**操作：** 打開 StockToken.sol，依序找 `pricePerShare`、`mint`、`redeem`。指向 `totalTwdReserve` 與 `insufficient reserve`，先埋下最後討論的線索。

### 25｜5-3 Factory 合約（Canva 34；84:00–87:00）

如果要建立很多檔股票，不必每次手動複製一份合約。Factory 提供同一套建立流程，收到股票代號、名稱與代幣代號後，建立一個新的 StockToken，並記錄代號對應的合約地址。

這個專案的 createStock 是管理者呼叫，一次建立一檔。各檔共用 TWD 與 Oracle，但每檔有自己的地址與儲備。統一模板讓規則一致，不代表所有資產都放在同一份 ERC-20 帳本裡。

**提問：** 建立台積電和鴻海之後，預期看到一個還是兩個 StockToken 地址？

### 26｜5-4 批次建立代幣（Canva 35；87:00–91:00）

這裡的批次，是部署腳本對股票清單跑迴圈：準備代號，呼叫 createStock，等待交易，再讀新地址。它減少人的重複操作，但鏈上仍是多筆交易；中間某筆失敗，不會自動撤銷前面已經完成的所有交易。

最後腳本把地址和 ABI 寫到 deployed.json，前端就知道要連哪些合約。課堂我只帶大家看兩檔的流程，完整結果先準備好，避免大家把時間花在等待十二檔部署。

**操作：** 左側開 `stocks.js`，右側開 `deploy.js`；找到 `for`、`.wait()`、`tokenOf`、`writeFileSync`。不要在課堂重跑完整部署覆蓋目前使用的地址。

### 27｜5-5 前端串接與交易：介面（Canva 36；91:00–99:00）

現在請開精簡前端。它用純 HTML 和 ethers，先讓大家看清楚地址、ABI 和讀寫流程；完整專案另外用 React、wagmi 與 viem。兩份介面使用的概念相同，今天先從比較短的版本學起。

先貼你自己的 ClassToken 地址，讀名稱與餘額。接著看台股區塊：選標的、讀價格、領測試 TWD。付款金額先填 1000，按第一步授權。大家先停在這裡：餘額有沒有減少？額度是不是增加了？這個停頓很重要。

**操作：** 終端執行 `node workshop/frontend/serve.mjs`，開 `127.0.0.1:4173`。先示範再留 4 分鐘學生操作；兩人一組也可。VM 發幣的學生先看講師的 Sepolia 實例，不把 VM 地址硬貼進來。

### 28｜5-5 前端串接與交易：交易流程（Canva 37；99:00–105:00）

現在按買入。錢包確認後，前端收到 hash，等待 receipt，確認成功後再刷新餘額與授權額度。若價格剛好是 1000 TWD，每次付款 1000 約得到一股；實際數量仍以合約執行時價格為準。

請打開 app.js，找到 approve、mint 和 receipt。這幾段把剛剛的畫面串起來：網路與地址選對，ABI 告訴我們怎麼呼叫，signer 代表誰簽署。網站顯示成功的依據應該是交易結果，不是按鈕已經被點過。

**操作：** 留 3 分鐘完成買入，最後由講師示範贖回。若出現 stale price，停下說明 Oracle 時效；如果出現儲備不足，留待最後風險討論，不反覆重送。問同學：前一筆 approve 會因為後一筆 mint 失敗而自動取消嗎？不會。

## 105–112 分鐘｜第六單元：預言機與 DeFi 整合

### 29｜6-1 價格資料上鏈（Canva 38；105:00–106:00）

合約不會自己打 HTTP 去抓 TWSE。鏈下 feeder 取得資料，授權帳戶把 price、decimals 寫入 PriceOracle，合約再讀取。這就是外部世界與合約之間的資料入口。

看程式的 onlyFeeder，這個原型採授權餵價。它讓我們知道誰可以寫，不代表寫進來的內容一定正確。

### 30｜6-2 價格精度與時效（Canva 39；106:00–107:00）

同一個數字要配精度才有意義：235500 配 decimals 2，表示 2355.00。updatedAt 用來看資料寫入時間；價格太舊，StockToken 會拒絕使用。

本專案 maxPriceAge 預設是 30 天，這是目前程式的設定，不是所有金融產品都適用的標準。設計時要依資產和用途選擇容許時間，也要考慮餵價中斷時系統怎麼處理。

### 31｜6-3 抵押與借款（Canva 40；107:00–108:00）

借貸池可以接受股票代幣作抵押，再借出 TWD。本專案預設 LTV 50%，假設抵押價值 10000，理論借款上限是 5000；實際仍受池中資金及其他條件限制。

抵押不是把風險消掉，只是讓借款有一份可處理的擔保。抵押品價格下降時，借款人的風險會上升。

### 32｜6-4 健康因子（Canva 41；108:00–109:30）

看同一個例子：10 股、每股 1000、借款 4000，先忽略利息。清算門檻 65%，健康因子就是 10000 乘 65% 再除以 4000，得到 1.625。

若每股跌到 600，抵押價值剩 6000，算出 0.975，小於 1，部位就符合可清算條件。50% 的借款上限和 65% 的清算門檻是不同參數，不要混在一起。

### 33｜6-5 清算機制（Canva 42；109:30–110:30）

當健康因子低於門檻，清算者可以依合約規則代償債務，換取部分抵押品與獎勵。本專案預設獎勵 5%，但實際可處理的數量仍受部位和合約條件限制。

清算不是合約自行醒來。需要外部帳戶或 keeper 發交易，也需要資金與 gas。這就是我們在架構圖另外畫出 keeper 的原因。

### 34｜6-6 預言機信任邊界（Canva 43；110:30–112:00）

最後把這段串起來：來源資料、授權餵價者、Oracle 合約，到使用價格的應用，每一段都要看。鏈上交易能告訴我們誰在什麼時候寫入，卻不能自動替來源資料背書。

所以看 Oracle 至少問三件事：價格是否正確、是否夠新、誰能更新。本原型不是去中心化預言機網路，而是授權餵價的實作。接著我們再問另一個獨立問題：即使價格完全正確，有沒有錢付？

## 112–120 分鐘｜第七單元：儲備、權限與風險檢驗

### 35｜7-1 儲備缺口（Canva 44；112:00–113:30）

回到一開始的問題。只看一個隔離例子：發出一股時收到 1000 TWD，後來價格漲到 1200，沒有任何額外資金進來。儲備仍是 1000，但想贖回需要 1200，中間差 200。

這時程式會擋下贖回。Oracle 可以把報價改成 1200，不能把資金變成 1200。要解決缺口，必須真的設計資金來源和儲備管理機制。甚至直接轉 TWD 給合約，也不會自動增加程式裡的 totalTwdReserve 記帳；要看目前實作是否支援那條路徑。

### 36｜7-2 管理者權限（Canva 45；113:30–114:30）

讀合約時不只看使用者能做什麼，也看管理者能做什麼。這份 StockToken 的黑名單會擋轉入轉出，包括鑄造與銷毀對象；pause 只套在 mint 與 redeem，一般 transfer 沒有因此全部停掉。

kycVerified 在這份程式裡是標記資料，並不是強制轉帳門檻。不要因為看到函式叫 setKyc，就說已經完成完整合規系統。判斷功能要看它實際在哪些執行路徑被檢查。

### 37｜7-3 資產與兌付制度（Canva 46；114:30–115:30）

如果要把教學原型變成真實產品，還要回答：誰保管資產、持有人有什麼權利、誰負責兌付，以及如何驗證。這些不是把前端畫漂亮或再部署一份合約就會自動完成。

程式規則、鏈上餘額和現實履約是相互連接的部分。今天我們完成的是可讀、可操作的技術原型，也知道哪些承諾還沒有被實作。

### 38｜7-4 錢包安全（Canva 47；115:30–116:00）

最後提醒三個操作習慣：核對官方網址、看清授權對象與額度、自己妥善保存復原資料。課程用新錢包與測試資產，不把真實資產帳戶拿來試陌生合約。

### 39｜7-5 成果回顧與討論（Canva 48；116:00–117:00）

今天你已經走過錢包、ERC-20、台股代幣、前端與風險檢查。你現在應該能說明：代幣在哪份合約裡、交易由誰簽署、價格從哪裡來，以及贖回資金是否真的存在。

如果只能帶走一個習慣，請每次看到 RWA 應用時都追問：價格可信嗎？儲備足夠嗎？權利清楚嗎？這些問題能讓你同時看懂技術與產品的責任。

## 講師備用回答

**智能合約是否一定不可修改？** 這份部署的程式不會隨本機檔案自動改變；有些系統另外設計升級代理，必須檢查實際架構，不能概括所有合約。

**有 KYC、pause 就代表正式金融商品嗎？** 不代表。它們是技術控制能力，現實權利、責任與制度需要另外成立；本課不替特定產品作法律認定。

**今天的幣有市場價值嗎？** 課程只把它當測試資產；能發幣不代表有人承諾兌付，也不代表有市場需求。

**為什麼台股畫面價格和鑄造價格可能不同？** 畫面 API、鏈上 Oracle、AMM 池價是不同路徑，要查各自來源、更新時間和使用目的。

**買入失敗，授權為何還在？** approve 和 mint 是兩筆交易。後一筆失敗不會撤銷前一筆已成功的授權。

**原專案還有 IPO、Swap、AI 風險功能，今天為何沒全部實作？** 兩小時優先讓同學完成發幣和前端讀寫；其餘程式完整保留，課後可從目錄及函式索引繼續看。AI 評語沒有自動修改鏈上 LTV。
